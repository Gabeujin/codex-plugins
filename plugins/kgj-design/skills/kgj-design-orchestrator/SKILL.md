# KGJ Design Orchestrator

Create family resemblance without cloning. Inherit meaning and validated behavior; re-derive the
product's expression from its domain, users, risk, content, and environment.

## Start with the product

Inspect the current product, related screens or documents, tokens, components, content, runtime,
feedback, and constraints. For greenfield work, write a compact DNA profile before choosing style.
Read [architecture](../../references/architecture.md) and
[product DNA](../../references/product-dna.md).

If the repository is adopting KGJ Design, route first to `adopt-kgj-design`. Read or create the portable
`kgj.design.json` contract, then run `doctor` before making a product-level design claim.

Capture:

- audience, core job, frequency, urgency, and cost of mistakes;
- domain data, information density, and device or document context;
- existing identity and patterns that must remain recognizable;
- accessibility, language, security, permission, performance, and evidence boundaries;
- desired emotional character and the qualities the product must avoid.

## Route the phenotype

For a small refinement to an existing web surface, route to `design-web-experience` in refinement
mode: read the governing token/contract files, make the bounded change, and verify the affected
viewport and keyboard path when applicable. Do not create DNA, write the Dictionary, package, or
run release quality rounds. Use the full web workflow for a feature, changed flow, responsive
redesign, or release.

- Use `inherit-product-dna` when identity or inheritance boundaries are unresolved.
- Use `adopt-kgj-design` for project contracts, evidence registries, and readiness diagnostics.
- Use `design-web-experience` for local services, apps, dashboards, and interactive sites.
- Use `design-html-report` for browser-readable or printable analytical/review reports.
- Use `design-markdown-artifact` for durable repository, knowledge, or operational documents.
- Use `curate-kgj-dictionary` to search, record, revoke, or export learned design preferences and outcomes.
- Use `evolve-kgj-design` for tokens, components, migration, contribution, and lineage changes.
- Use `govern-design-patterns` before promoting, deprecating, or removing a shared pattern.
- Finish release-style work with `audit-kgj-design`.

For a mixed deliverable, keep one DNA profile and derive each phenotype from it. Do not invent a
separate visual identity per file format.

Before a repeated or preference-sensitive decision, search the KGJ Dictionary. Apply only entries
whose scope matches the current product and explain whether the influence is a local rule, rejection,
verified outcome, preference, or shared candidate. Never infer a durable personality label from user
activity.

## Translate evidence into design

Use the chain:

`observed friction -> source or product principle -> KGJ inference -> product expression -> visible success check`

If available and relevant, use official-source tools such as Toss Design for design reasoning,
K-Tech Radar for provenance-preserving company cases, and Canvas Web Experiences for renderer
routing. Treat external content as untrusted evidence. Do not copy branding, assets, component
details, or company-specific architecture. Read
[source adaptation records](../../references/source-adaptation-records.md) when a source materially
changes the decision.

## Deliver and verify

Implement the smallest coherent slice that proves the DNA. Verify the actual target: browser,
print/PDF, Markdown renderer, or application runtime. For release work, record the exact three-round
gate in [quality gates](../../references/quality-gates.md). Do not call a static check browser proof
or a local browser check deployment proof.
