# Codex 기능 Daily Check

Return a source-backed checklist within a 300-second target. Capture the actual turn-start epoch when the host exposes it; otherwise capture time in the first tool call and explicitly disclose any excluded pre-tool setup. Never invent or backdate an epoch, and never label helper-only time as full turn duration. Plugin creation/repair is separate from this timed run. Start a wall-clock deadline BEFORE discovery. Stop starting probes at 240 seconds and finalize by 300 seconds; a blocked host call can exceed this target, so report the actual elapsed time and never promise a hard SLA. Each call gets at most 20 seconds where supported; one recovery only if time remains. No model-catalog/model jobs, installs, upgrades, config changes, service restarts, cache deletion, schedules, or external messaging inside the timed diagnostic phase. If an installed feature fails, finalize the diagnostic on time and continue a separately timed official-documentation-based recovery phase when the user requested repair/normalization; do not stop at a suggestion when an authorized safe repair is possible. For a diagnostic-only invocation, preserve failures and propose concrete repair steps without changing configuration. Read [recovery.md](references/recovery.md).

## Start and evidence

Resolve the plugin root from the loaded SKILL.md path: `Path(skill_file).resolve().parents[2]`. Scripts are `<plugin-root>/scripts`, NOT `<plugin-root>/skills/codex-daily-check/scripts`. Verify `report.py` and `probe.py` exist once; reuse these exact absolute paths. Use the existing Python runtime; do not install dependencies. Create a unique run directory outside the installed plugin cache, under a user-selected run store (for example `%LOCALAPPDATA%/CodexDailyCheck/runs` on Windows or `~/.local/state/codex-daily-check/runs` elsewhere). The helper exclusively creates new files and does not overwrite old reports. Receipts are caller-recorded observations, not signed, tamper-evident or independent runtime certification. Do not overwrite previous runs. Save only allowlisted diagnostic facts, tool names and schema hashes; never save the whole environment, credentials, unrelated window titles, page contents, or user answers. Compare only the previous finalized run under the same machine/profile scope.

Capture the diagnostic start Unix epoch before discovery and pass it as `--started-epoch <epoch>` to `scripts/report.py start --root <run-store> --capabilities <json-file>`; add `--computer-installed` when the actual installed plugin inventory confirms Computer Use. The capabilities JSON is an array of `{name, schemaHash}` for currently callable tools (hash complete exposed descriptions/schemas; missing hashes mean name-only comparison). Call the helper with `--help` if needed. Keep the returned run path and deadline. Capabilities are a UTF-8 JSON FILE, never an inline shell-escaped JSON string. Write with a structured file API or Python `json.dump`; parse and read back before passing its path. Include exposed top-level tools such as `functions.request_user_input_async` as well as discovered tools: absence from `ALL_TOOLS` alone does not prove unavailability. If inventory capture fails, preserve the error and continue without it; do not spend the budget copying a large tool catalog. Final outputs are `final.json` and `report.md` after finalize, never `report.json`. Start without an inventory if unavailable, but record discovery as UNKNOWN. Initial rows must remain UNKNOWN until evidenced.

## Host capability gate

Apply this skill to the tools actually exposed in this Codex session. First identify OS, interactive desktop availability, Python executable, browser providers, installed Computer Use route and user-question tools. Do not infer these from the model name or from Codex being installed. On Windows use the Windows native helper only with an interactive Windows desktop; never invoke WinForms/NotifyIcon on macOS, Linux, WSL or cloud. Other native providers can be checked only through their exposed official skills, using a task-owned document in a supported app rather than assuming Notepad exists. CLI/cloud sessions without desktop/browser tools still run portable execution, UTF-8, version and receipt checks. Record unavailable rows with the exact environment reason and continue; do not crash or install dependencies to make a diagnostic run.

No Python or shell: use available tools for safe probes and produce the same checklist in the response, explicitly stating that persistent helper receipts could not be generated. Do not fabricate a file link. No async question tool: a normal user reply may establish `codex.input` through that conversation route, but never establishes the async-tool route or OS notification. Coordinate using the host's supported user-input mechanism; if none is available, defer foreground work. A Plan-only tool is usable only in its allowed mode. A new Desktop task may expose updated tools, but do not promise that it will fix a missing tool.

Distinguish FAIL (observed operation failure), BLOCKED (policy), UNAVAILABLE (session/platform lacks the route), and missing observation (UNVERIFIED/NOT_TESTED/DISPATCHED). PARTIAL means incomplete coverage, not that all functionality failed. Keep the full READY gate; never hide unsupported rows or turn them into PASS. Portable diagnostic usability does not certify every GUI feature on every Codex host.

## Parallel execution plan

Use one coordinator and parallel tool calls, not extra model sessions. The 300-second budget includes setup, recovery, waits and final readback. It is a ceiling: finish earlier when the evidence is complete. Before any mouse/keyboard takeover, ask once for timing using an available async question: “마우스·키보드를 약 20초 사용해도 되는 시점을 알려 주세요.” Offer “지금 가능” and “이번에는 보류”. This is coordination of an already authorized test, not permission to perform unrelated actions. Continue background work while waiting, bounded by the original deadline. Record the readiness decision as a brief fact in `computer.input` evidence (no raw answer). Silence or elapsed time is not consent to take control. A prior explicit time window is sufficient; announce immediately before entering it. If the user is absent/busy, record native read/input NOT_TESTED with the timing blocker; never report PASS or seize control.

## Upgrade and regression handling

For CLI version lag, follow [CLI command-only policy](references/cli-update.md), including during recovery.

`report.py finalize <run>` compares capability names/schema hashes with the previous finalized snapshot. Added or changed tools become NEW_UNTESTED; removed tools become SESSION_UNAVAILABLE. Do not execute newly discovered mutating tools automatically. Hash changes prove a surface change, not runtime health. A changed version in the system receipt triggers REVIEW_REQUIRED. For plugin versions, capture named plugin versions as additional capability entries (for example `plugin:computer-use@VERSION`) or explicitly record their comparison; the tool inventory alone does not establish a plugin package version. Identify affected probes; version numbers alone never prove a feature works.

Compare standalone CLI with bundled CLI only when both versions parse and share comparable release channels. Desktop's app version is not a CLI version. Older standalone CLI means local version lag, not proof that the latest public release is missing. CLI updates are COMMAND-ONLY in this workflow. Compare standalone CLI against a successfully fetched official latest release, separately from the bundled CLI. When a newer stable release exists, supply the verified installation-specific update command and the post-update verification command only. Never execute the update, start an updater, alter npm/global PATH, or close/restart Codex Desktop on the user's behalf. On network, channel or install-source ambiguity, return UNKNOWN and explain what could not be verified; do not claim up-to-date or invent a package-manager command. For a verified npm global installation the suggested command is `npm install -g @openai/codex@latest`, followed by `codex --version` in a new terminal. The user owns application restart timing. A global CLI update does not by itself prove the separate Desktop-bundled executable was updated; do not claim that a Desktop restart universally changes its bundled CLI. When the user explicitly requests upgrade coverage, use remaining time to consult official OpenAI release notes, or queue that research outside daily mode. Record new documented features, source URL/date, exposure, harmless acceptance test, and `NEW_UNTESTED` until the test passes. Never claim all new features are covered from tool discovery alone.

## Output

Answer in Korean with separate actual-failure, policy-blocked, session-unavailable and missing-observation counts, elapsed time, overall readiness (READY only if all required operational rows pass; otherwise PARTIAL/ATTENTION), failed/unverified rows, recovery already performed, and 1–3 concrete remaining actions. Installed-feature failure must not end with unattempted repair suggestions when authorized non-disruptive work remains. Link the report. Separate timed daily results from setup/development tests. List native input test vs actual approval coverage explicitly. No unsolicited automation; this is an on-demand skill unless the user separately requests a schedule.

## Complete verification gate

All non-legacy rows, including genuine approval, must pass before READY. A five-minute diagnostic completion is not full verification. If host policy forbids requesting approval (such as `never`), record the actual approval probe BLOCKED by session policy and explain that a separate user-configured approval-enabled session with a harmless, authorized operation is needed; do not change policy or manufacture a dangerous operation. Never treat question notifications as approval notifications. Preserve the timed receipt; supplemental verification gets a new receipt with its own timestamps and a link to the original run.

## Completion timing

300 seconds is the diagnostic ceiling, not a minimum duration; 180 seconds is not a cutoff. Start the deadline before discovery. Finish immediately when every required row has an evidence-backed final disposition and no safe in-budget probe can resolve a remaining uncertainty. Never end merely because three minutes elapsed. At each boundary compute remaining time; reserve 30 seconds for persisting and reading back the final report. Do not launch probes after 240 seconds; collect already-running responses until 270 seconds, then finalize. A BLOCKED/UNVERIFIED disposition completes diagnosis, not full verification or READY.
