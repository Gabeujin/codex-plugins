# Codex 기능 Daily Check

Return a source-backed checklist within a 300-second target. Plugin creation/repair is separate from this timed run. Start a wall-clock deadline BEFORE discovery. Stop starting probes at 240 seconds and finalize by 300 seconds; a blocked host call can exceed this target, so report the actual elapsed time and never promise a hard SLA. Each call gets at most 20 seconds where supported; one recovery only if time remains. No model-catalog/model jobs, installs, upgrades, config changes, service restarts, cache deletion, schedules, or external messaging inside the timed diagnostic phase. If an installed feature fails, finalize the diagnostic on time and continue a separately timed official-documentation-based recovery phase when the user requested repair/normalization; do not stop at a suggestion when an authorized safe repair is possible. For a diagnostic-only invocation, preserve failures and propose concrete repair steps without changing configuration. Read [recovery.md](references/recovery.md).

## Start and evidence

Resolve the plugin root two levels above this file's skill directory. Use the existing Python runtime; do not install dependencies. Create a unique run directory outside the installed plugin cache, under a user-selected run store (for example `%LOCALAPPDATA%/CodexDailyCheck/runs` on Windows or `~/.local/state/codex-daily-check/runs` elsewhere). The helper exclusively creates new files and does not overwrite old reports. Receipts are caller-recorded observations, not signed, tamper-evident or independent runtime certification. Do not overwrite previous runs. Save only allowlisted diagnostic facts, tool names and schema hashes; never save the whole environment, credentials, unrelated window titles, page contents, or user answers. Compare only the previous finalized run under the same machine/profile scope.

Use `scripts/report.py start --root <run-store> --capabilities <json>`; add `--computer-installed` when the actual installed plugin inventory confirms Computer Use. The capabilities JSON is an array of `{name, schemaHash}` for currently callable tools (hash complete exposed descriptions/schemas; missing hashes mean name-only comparison). Call the helper with `--help` if needed. Keep the returned run path and deadline. Start without an inventory if unavailable, but record discovery as UNKNOWN. Initial rows must remain UNKNOWN until evidenced.

A host-specific fresh-session wrapper is optional (`--cli-wrapper`); use the supported local wrapper if the host requires one. Never assume a developer-specific path exists. Keep `browser.iab.read/navigation/input` and `browser.chrome.read/navigation/input` independent. Record provider/browser identity. Existing Chrome process control is not cold-start proof. |
| 105–150s | Installed Computer Use: real app | Mandatory when installed; discovery alone is insufficient. Read current computer-use SKILL and API. Use `node_repl` + `@oai/sky` independently from `cua` native availability. Launch Notepad, uniquely select its returned native window, create a NEW blank tab, focus it, type a unique token, and read the result through screenshot/accessibility. Preserve unrelated restored user tabs. If accessibility is null, use the documented screenshot path; don't declare native control unavailable. If time allows, save to a new run file and compare UTF-8 exactly. Do not use the PowerShell notification form as this acceptance target. Any real failure starts the recovery workflow. |

| 215–240s | Codex input/approval and changes | If `request_user_input_async` is callable, ask one short diagnostic feedback question about visibility or interaction; it works independently of Plan-only `request_user_input`. Ask for missing user observation, not permission. Record an actual response separately. App question card is not Windows-native input. The optional bundled `assets/browser-check.html` is useful only on a surface that permits local files; the mandatory browser probes do not depend on it. Browser file URLs may be blocked. If rejected by security policy, mark the local-fixture probe BLOCKED; never route the same content through loopback, another browser, CDP or alternate transport to evade that policy. An independent public-page read/navigation probe at https://example.com may establish only that narrower browser coverage; it does not pass the blocked local form-input probe. Do not substitute an HTTP client, Playwright from a different transport, or browser JavaScript execution as proof of the requested browser-control route.

The standalone Windows form/balloon is a diagnostic fallback, not Codex's own Windows toast/approval implementation. Record `native.simple`, `native.response`, `codex.input`, `codex.notification`, and `codex.approval` separately. A dedicated notification tool is not required to test Codex notifications: a real `request_user_input_async` question may trigger the app's own OS notification. Ask the user to minimize the app, allow a brief switch-away interval, send one diagnostic observation question, and collect whether a Windows notification appeared and whether responding required opening the app. A user-provided screenshot can corroborate the displayed app identity, message, and controls. An in-app card while foregrounded is not a notification failure. Mark `codex.notification` PASS only for the observed notification category (for example question), and record completion/permission categories separately in evidence as untested when appropriate. No inline reply field means that shown toast does not establish inline reply support; never conflate a click-to-app response with an inline response. If no supported trigger or observation is available, record UNVERIFIED with the exact blocker, not a blanket product-wide UNAVAILABLE. Official reference: https://learn.chatgpt.com/docs/notifications. `functions.notify` is tool output, not an OS notification. Never use external Slack/email messages for this check.

For each result call `scripts/report.py record <run> --id <id> --status <status> --evidence <brief fact>`. Readback is mandatory. Allowed statuses: PASS, FAIL, BLOCKED, UNAVAILABLE, UNVERIFIED, NOT_TESTED, UNKNOWN, DISPATCHED. Include the exact error class and practical next step, without private data. Import success cannot pass computer.read/input; tab open cannot pass browser read/navigation/input. Record actual installed Computer Use failures with both `official-docs:` and `normalization:` evidence as described in recovery.md; unavailable documentation is itself explicit evidence, not a reason to drop the error. No response is not FAIL. A missing tool is unavailable in this session, not necessarily broken globally.

## Upgrade and regression handling

For CLI version lag, follow [CLI command-only policy](references/cli-update.md), including during recovery.

`report.py finalize <run>` compares capability names/schema hashes with the previous finalized snapshot. Added or changed tools become NEW_UNTESTED; removed tools become SESSION_UNAVAILABLE. Do not execute newly discovered mutating tools automatically. Hash changes prove a surface change, not runtime health. A changed version in the system receipt triggers REVIEW_REQUIRED. For plugin versions, capture named plugin versions as additional capability entries (for example `plugin:computer-use@VERSION`) or explicitly record their comparison; the tool inventory alone does not establish a plugin package version. Identify affected probes; version numbers alone never prove a feature works.

Compare standalone CLI with bundled CLI only when both versions parse and share comparable release channels. Desktop's app version is not a CLI version. Older standalone CLI means local version lag, not proof that the latest public release is missing. CLI updates are COMMAND-ONLY in this workflow. Compare standalone CLI against a successfully fetched official latest release, separately from the bundled CLI. When a newer stable release exists, supply the verified installation-specific update command and the post-update verification command only. Never execute the update, start an updater, alter npm/global PATH, or close/restart Codex Desktop on the user's behalf. On network, channel or install-source ambiguity, return UNKNOWN and explain what could not be verified; do not claim up-to-date or invent a package-manager command. For a verified npm global installation the suggested command is `npm install -g @openai/codex@latest`, followed by `codex --version` in a new terminal. The user owns application restart timing. A global CLI update does not by itself prove the separate Desktop-bundled executable was updated; do not claim that a Desktop restart universally changes its bundled CLI. When the user explicitly requests upgrade coverage, use remaining time to consult official OpenAI release notes, or queue that research outside daily mode. Record new documented features, source URL/date, exposure, harmless acceptance test, and `NEW_UNTESTED` until the test passes. Never claim all new features are covered from tool discovery alone.

## Output

Answer in Korean with elapsed time, overall readiness (READY only if all required operational rows pass; otherwise PARTIAL/ATTENTION), failed/unverified rows, recovery already performed, and 1–3 concrete remaining actions. Installed-feature failure must not end with unattempted repair suggestions when authorized non-disruptive work remains. Link the report. Separate timed daily results from setup/development tests. List native input test vs actual approval coverage explicitly. No unsolicited automation; this is an on-demand skill unless the user separately requests a schedule.

## Complete verification gate

All non-legacy rows, including genuine approval, must pass before READY. A five-minute diagnostic completion is not full verification. If host policy forbids requesting approval (such as `never`), record the actual approval probe BLOCKED by session policy and explain that a separate user-configured approval-enabled session with a harmless, authorized operation is needed; do not change policy or manufacture a dangerous operation. Never treat question notifications as approval notifications. Preserve the timed receipt; supplemental verification gets a new receipt with its own timestamps and a link to the original run.

## Adaptive five-minute execution

300 seconds is the diagnostic ceiling, not a minimum duration; 180 seconds is not a cutoff. Start the deadline before discovery. Finish immediately when every required row has an evidence-backed final disposition and no safe in-budget probe can resolve a remaining uncertainty. Never end merely because three minutes elapsed. At each boundary compute remaining time; reserve 30 seconds for persisting and reading back the final report. Do not launch probes after 240 seconds; collect already-running responses until 270 seconds, then finalize. A BLOCKED/UNVERIFIED disposition completes diagnosis, not full verification or READY.

Batch independent version/file reads. Do not run agents, model-catalog checks, duplicate whole test suites or release research inside the diagnostic. Keep IAB and Chrome identities independent and use fresh observed indices with minimal read-action-read round trips. Never parallelize competing desktop focus/input actions or show a foreground native form while controlling another app. Launch the native human form yieldably after native app input, then perform independent read-only aggregation while the human responds. Test Codex question OS notifications after an explicit switch-away opportunity, without losing the original deadline. Reuse already-read tool/skill documentation; do not reload large documentation during the same run unless state changed. A tool-level deadline cannot forcibly cancel every host/browser call, so report a measured overrun as failure to meet the target rather than fabricating a duration. Long repairs or prerequisite installation remain outside the timed phase.
